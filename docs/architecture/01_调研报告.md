## 0. 项目一句话定义

一个网页版多人聊天室,但聊天室里是 **"用户 + 一群 AI"**。多个 AI 角色在同一个聊天室互动,用户可主动 `@某 AI`,AI 之间可互相 `@`、回应、挑刺;所有发言流式输出;可视化讨论过程 + 一键导出结构化纪要。

## 1. 多 Agent 编排框架选型

### 1.1 候选框架对比

| 维度 | **LangGraph** (multi-agent supervisor) | **CrewAI** | **OpenAI Agents SDK** |
|---|---|---|---|
| 核心抽象 | `StateGraph` 节点 + 边 (DAG) | `Agent` + `Task` + `Crew` + `Process` | `Agent` + `Handoff` + `Guardrail` |
| 调度模式 | Supervisor 路由 / 条件边 / 循环 | sequential / hierarchical / parallel | 移交 (Handoff) / Agent-as-Tool |
| 流式输出 | 原生 `stream_mode=custom/values` 节点级 | `kickoff` 一次性返回,可拆 async 包装 | `Runner.run_streamed()` 实时流 |
| 状态管理 | `TypedDict` + Reducer + Checkpointer (Postgres/Redis) | 短/长/实体记忆 (内置) | 外部化 Session 状态 |
| 角色扮演 | 通过 prompt + node 实现 | 一等公民 (role/goal/backstory) | 通过 instructions 实现 |
| 厂商绑定 | LangChain 生态(支持 100+ 模型) | LangChain 生态(支持 100+ 模型) | 任意 OpenAI Chat Completions 兼容模型 (LiteLLM/any-llm) |
| 学习曲线 | 中(图论思维) | 低(直白) | **最低**(核心 3 个原语) |
| Tracing | 需 LangSmith (付费) | 无内置 | **内置免费 Tracing** |
| Human-in-the-Loop | 需 `interrupt_before` 手写 | `human_input=True` | 内置审批机制 |
| 群聊适配度 | ★★★★★(天然支持 supervisor + 条件边决定谁说话) | ★★★☆☆(sequential 不适合自由发言) | ★★★★☆☆(Handoff 适合接力) |
| 官方仓库 | github.com/langchain-ai/langgraph | github.com/joaomdmoura/crewai | github.com/openai/openai-agents-python |
| 文档 | langchain-ai.github.io/langgraph | docs.crewai.com | openai.github.io/openai-agents-python |

**关键 Demo 验证**(都看过了):
- **LangGraph**: Supervisor 模式官方教程 — `langgraph_supervisor` 库 + 自定义 `StateGraph` 都跑通,`stream_mode="custom"` 能在节点执行时 `writer({...})` 推送自定义事件([来源](https://langchain-ai.github.io/langgraph/tutorials/multi_agent/agent_supervisor/))。
- **CrewAI**: 4 个角色 (Researcher / Writer / Reviewer / Tester) hierarchical 模式跑得通,`output_json=Pydantic` 可锁死输出结构。
- **OpenAI Agents SDK**: `Handoff` 实现"问题分流 → 翻译 Agent",`Guardrail` 用 Pydantic + LLM 做内容安全检查,`Runner.run_streamed` 流式输出事件 (`ResponseTextDeltaEvent`)。

### 1.2 推荐方案 — **LangGraph multi-agent supervisor**

**核心理由**(5 条):
1. **群聊是图问题,不是流水线**。群聊调度是"用户发言 → 谁来回应 → 下一个谁说 → 是否结束"的有状态图,CrewAI 的 sequential/hierarchical 强行套上去会非常别扭,LangGraph 的 `add_conditional_edges` 是为这种动态路由而生的。
2. **流式 + 节点级事件**。`stream_mode="custom"` 允许每个 Supervisor 决策、每个 Agent 思考/输出阶段都 `writer({...})` 推送事件到前端,这是"打字机效果"的关键。
3. **Checkpointer 天然支持断点续传**。`InMemorySaver` / `PostgresSaver` 让会话状态可恢复,流式输出中断后可以从最后状态续上 — 直接解决"流式断点续传"难点。
4. **Reducer 解决并发乱序**。`Annotated[list, add]` 让多个 Agent 写共享消息列表时不会互相覆盖 — 解决"多 Agent 并发乱序"难点。
5. **学一次,覆盖三种调度策略**。Round-robin、Supervisor 决定、自由发言,都是 `add_conditional_edges` 换不同 routing 函数而已。

**为什么不是 CrewAI**:CrewAI 的 Process 是 task 级的(整段任务一次性跑完),不适合"每个 Agent 轮流说一句话"的颗粒度。
**为什么不是 OpenAI Agents SDK**:Handoff 是"任务移交"语义(任务做完整个转交),不是"一个 Agent 插一句话"。Guardrail + Tracing 确实很香,但群聊场景发挥不出来;真要做多供应商可以后面接 any-llm。

## 2. 前端 / 实时流式方案选型

### 2.1 实时通信技术对比

| 维度 | **WebSocket** | **SSE (Server-Sent Events)** | 长轮询 |
|---|---|---|---|
| 方向 | 全双工 | 单向 (server→client) | 单向 |
| 协议 | ws:// / wss:// | HTTP (text/event-stream) | HTTP |
| 复杂度 | 中 (握手 + 心跳) | 低 (EventSource 原生) | 高 (频繁建连) |
| 浏览器并发 | 无硬限 | Chrome/Firefox 每域 6 个连接硬限 | 无 |
| LLM 流式 | 可用,但需自己分包 | **天然契合** (ChatGPT 用的就是它) | 不合适 |
| 适用场景 | 聊天室/协作编辑 | 流式输出/通知/进度 | 兼容老旧浏览器 |

**关键洞察**:ChatGPT 的"打字机效果"就是 SSE。LLM 流式输出是典型的"server 单向持续推"场景。

### 2.2 群聊项目特殊点

群聊同时需要:
- **客户端发消息** (用户发言、@某 AI) — 需要上行
- **服务端推流** (AI 思考中 / AI 逐字输出) — 需要下行

**两种架构**:
- **A. 纯 WebSocket**(推荐):一条长连接双向全搞定,前端最简单。前端代码量最少,后端用 FastAPI `@app.websocket`。
- **B. WebSocket + SSE 混用**:WS 收用户消息,SSE 收流式输出。过度设计,前阶段不要。

### 2.3 UI 框架对比

| 维度 | **Next.js 15 + React 19** | **Streamlit** | **Gradio** | **纯 HTML + Tailwind + Vanilla JS** |
|---|---|---|---|---|
| 实时性 | ★★★★★(SPA + WS) | ★★★☆☆(rerun 机制,延迟高) | ★★★☆☆(queue + 轮询) | ★★★★★ |
| 复杂度 | 中 (Next 路由 + 状态) | 低 (Python 写 UI) | 低 (config 写 UI) | 低 (无框架) |
| 视觉可控 | ★★★★★ | ★★☆☆☆(千篇一律) | ★★☆☆☆(模板化) | ★★★★★ |
| 流式渲染 | 自己实现(可控) | 框架包装(不可控) | 框架包装(不可控) | 自己实现(可控) |
| 适合"作品集" | ★★★★★(简历可写) | ★★☆☆☆ | ★★☆☆☆ | ★★★☆☆ |
| 部署 | Node + 静态资源 | Python 一把梭 | Python 一把梭 | 静态文件 |
| 学习成本 | 中 | 极低 | 极低 | 极低 |

### 2.4 推荐方案 — **Next.js 15 (App Router) + Tailwind + WebSocket 客户端**

**核心理由**:
1. **作品集需要颜值 + 可讲故事**。Streamlit/Gradio 一眼就是 demo,简历官看到会扣分。Next.js 是"产品级"前端,放在简历里是加分项。
2. **流式渲染的微观控制**。"打字机效果"、光标闪烁、骨架屏、思维链折叠 — 这些体验细节只有自定义 React 组件能做好,Streamlit/Gradio 的封装层会卡住你。
3. **与 FastAPI WebSocket 通信极简**。前端 `new WebSocket('ws://...')`,后端 `@app.websocket('/ws/{session_id}')`,中间纯 JSON 消息。
4. **部署友好**。`next start` + `uvicorn main:app`,Docker Compose 一把梭。

**后端栈配套**:
- Python 3.11+
- FastAPI 0.115+ (WebSocket + 流式)
- LangGraph 0.2+ (Agent 编排)
- LangChain 0.3+ (LLM 抽象)
- OpenAI / Anthropic / DeepSeek API (可切换)
- SQLModel + SQLite (持久化讨论纪要)

### 3.4 AgentVerse
- **GitHub**: https://github.com/OpenBMB/AgentVerse

## 4. 关键技术决策表

| # | 决策项 | 选择 | 关键理由 | 风险 / 备选 |
|---|---|---|---|---|
| 1 | 多 Agent 框架 | **LangGraph (multi-agent supervisor)** | 图结构 + 节点级流式 + Checkpointer + Reducer 完美匹配群聊 | 备选 OpenAI Agents SDK (更轻但调度灵活度低) |
| 2 | 实时通信协议 | **WebSocket (双向)** | 群聊需要双向,SSE 单向不够 | 后期可混 SSE (流式输出走 SSE,用户消息走 POST) |
| 3 | 前端框架 | **Next.js 15 + React 19 + Tailwind** | 作品集需要颜值 + 流式渲染细节控制 | 备选纯 HTML+JS (更快但视觉粗糙) |
| 4 | 后端框架 | **FastAPI 0.115+** | 原生 WebSocket 装饰器 + async 适合 LLM 流式 | 备选 Flask-SocketIO (成熟但慢) |
| 5 | LLM 抽象 | **LangChain ChatModel 接口** | 一行切换 OpenAI / Anthropic / DeepSeek / Ollama | 备选直接调 OpenAI SDK (绑死) |
| 6 | 持久化 | **SQLite + SQLModel (MVP) → Postgres (上线)** | MVP 阶段零配置,后期可平滑迁移 | 直接 Postgres 增加部署复杂度 |
| 7 | Agent 角色数 | **4 个 (主持人/创意/批判/总结)** | 群聊 >5 人会变吵,<3 人没"讨论感" | 可配置 (YAML 加载) |
| 8 | 调度策略 MVP | **主持人决定 (Supervisor)** | 讨论质量最可控,符合"主持人 Agent 调度"需求 | 备选 Round-robin (太机械) / 自由发言 (太混乱) |

## 5. 难点预判 (为架构设计铺垫)

### 5.1 多 Agent 并发乱序
- **现象**: 用户在 t=0 发消息,Agent A t=0.5s 回应,Agent B t=0.6s 回应,如果两个并发触发,前端收到顺序可能是 B→A。
- **解法**: (a) **串行调度** — MVP 阶段强制一个 Agent 说完再让下一个说话(LangGraph 的 `add_edge` 天然支持);(b) **消息带 `created_at` 时间戳** + 客户端排序;(c) LangGraph `Annotated[list[Message], add]` reducer 集中收集。

### 5.2 主持人 Agent 调度策略
- **三种候选**:
  - **Round-robin**: 简单但机械,讨论质量差
  - **主持人决定** (推荐): Supervisor LLM 看上下文决定下一个谁说,带明确"@" 触发规则
  - **自由发言**: LLM 看"谁最想回应这条消息" — 太不可控
- **MVP 选 "主持人决定"** + 提供 Round-robin 备选模式。

### 5.3 流式输出的断点续传
- **现象**: 网络抖动 → WS 断 → AI 正在说一半的话丢了。
- **解法**: (a) LangGraph Checkpointer 把 `graph.get_state(config)` 序列化为每条消息的 `last_event_id`;(b) 前端重连后发 `Last-Event-ID` 头(WS 协议借用 SSE 概念);(c) MVP 阶段先保证"断线重连后能继续讨论下一条",不追求逐字续传。

### 5.4 Token 成本控制
- **每轮 4 个 Agent × 1-3K tokens × 5-10 轮** = 一次讨论 20-120K tokens,成本不容忽视。
- **解法**: (a) 用 `gpt-4o-mini` / `claude-haiku` / `deepseek-chat` 等廉价模型做 MVP;(b) "总结者" Agent 只在最后一轮跑全量 context,中间轮用 summary 替代。

## 6. 调研结论

✅ **LangGraph multi-agent supervisor** 是本项目最契合的 Agent 编排框架。
✅ **Next.js + FastAPI + WebSocket** 是前端 + 后端 + 通信的最优组合。
✅ **5 个参考项目**提供了从 UI (TradingAgents-Studio) 到编排 (ChatDev) 到调度策略 (ChatEval) 的完整借鉴。
✅ **3 个核心难点**都有明确的技术解法,不存在"必须自研"的卡点。
